# Integration: gym_env → deadlock_resolution and mode_management

## Caller and callees

- **Caller**: `gym_env` (ir_gym in `gym_env/envs/ir_gym.py`).
- **Callees**: `deadlock_resolution` (DeadlockDetector, PARCoordinator, PARExecutor, PAREnvironment, CBSCoordinator, RuleBasedSequentialCoordinator), `mode_management` (StateManager, ModeController).

## Where and how they are used

- **When**: Only when `enable_deadlock_resolution=True`. On env construction, `_initialize_deadlock_modules()` creates DeadlockDetector, PARCoordinator, PARExecutor, StateManager, ModeController; PARCoordinator is given a PushAndRotate instance (from python_pnr) and config; PARExecutor is given config and dependencies (state_manager, par_coordinator). Optional config file is loaded in `enable_deadlock_resolution_mode(config_file)`. If `config_file` is provided and `deadlock_config` was None (e.g. env created with `enable_deadlock_resolution=False`), a `DeadlockConfig` is created first so the file is loaded before re-initializing modules; this ensures `USE_CBS_INSTEAD_OF_PAR` and CBS coordinator are set correctly when enabling deadlock resolution after creation.
- **Step path**: In `_step_with_deadlock_resolution(action_list)`:
  1. Build `agent_states` and `neighbor_states` from robot_list (position, velocity, goal).
  2. Increment detector’s step_counter (or equivalent).
  3. For each agent in RL_RVO mode: call `DeadlockDetector.detect_deadlock`; if True, get participants via `get_deadlock_participants`. If the detector returns an empty list (e.g. because the candidate group size is below `MIN_PAR_PARTICIPANTS`), the env stays in pure RL for that detection. Otherwise, the env either calls `CBSCoordinator.prepare_cbs_execution` (if `USE_CBS_INSTEAD_OF_PAR` and `cbs_coordinator` is set) or `PARCoordinator.prepare_par_execution`; if solution success (CBS returns non-None, PAR returns result.success), call `StateManager.set_par_mode` for each participant and inject MAPF waypoints (CBS: continuous paths from `get_agent_path`; PAR: grid path converted via coordinator/executor or synchronized waypoint tuples when enabled).
  4. For each agent in MAPF mode: call `PARExecutor.execute_par_step` (legacy executor path) or, in the tuple-based PAR integration, use the env’s synchronized waypoint group to override per-agent goals while actions still come from RL with speed caps. If executor result has `set_position`, set robot position; otherwise use result `action` for velocity (or zero). Check PAR completion and optionally switch back to RL_RVO via StateManager.
  5. Run waypoint progression (long-range or MAPF-injected), then compute observation/reward/done for all agents (RL policy may be applied only to RL_RVO agents; MAPF agents follow executor output or tuple-based waypoint goals).
- **MAPF waypoint safety nuance**: For PAR-injected waypoint managers only, gym_env now blocks `force_switch` if the straight segment from the current agent position to the candidate next PAR waypoint crosses an occupied cell in the planner-aligned occupancy grid. This is an env-side integration guard to prevent RL execution from shortcutting through obstacles when PAR waypoints are force-advanced under stall conditions.
- **Single active PAR tuple nuance**: When PAR returns synchronized waypoint tuples, gym_env treats the resulting `_par_tuple_group` as a single active synchronized execution. While that tuple group is active, later deadlock detections may still be logged, but the env skips launching a new PAR solve for them instead of resetting the active tuple group. This is the current integration rule that avoids repeated `mapf->mapf` reinjection churn.
- **Debug contracts when `DEBUG_MODE=True`**:
  - `deadlock_check_traces`: one RL-agent deadlock-evaluation record per step, used for participant-selection diagnosis.
    - when a later deadlock trigger is suppressed because a PAR tuple group is already active, the trace records `solver_skipped_reason=active_par_tuple_group_in_progress` together with the active tuple participants and tuple index
  - `waypoint_progression_traces`: one agent-step waypoint progression record per step, including manager type, waypoint index/stay-step before and after `WaypointManager.update()`, `advancement_reason`, `update_waypoint_history()` call info, and post-step MAPF exit reason.
    - when the new PAR force-switch guard blocks a shortcut, the record also carries `force_switch_blocked_reason`, `force_switch_guard_next_goal`, and `force_switch_guard_occupied_cell`
    - when a stationary tuple member is being intentionally held while a moving subset follows a fresh PAR solve, the record uses `advancement_reason=stationary_hold`
  - `mapf_execution_traces`: one MAPF-agent record per step, including current goal vector, desired velocity, raw/applied action, actual post-step velocity, goal angles/projections for raw/applied/actual motion, distance delta to current goal, consecutive non-progress count, and same-step env-side execution flags such as speed-cap/yield application plus RVO neighbor/`vo_flag` context.
  - `tuple_progression_traces`: one active tuple-group record per step, including tuple index, per-participant distance to target, blocking participant IDs, `dominant_blocking_participant_id`, `dominant_blocking_distance_to_target`, max deficit to row completion, blocked-step counters, per-group thresholds (`blocked_force_switch_steps`, `final_row_release_steps`), and `row_advancement_reason` (`all_reached`, `blocked_force_switch`, `moving_subset_replan`, `final_row_release`, `none`).
  - when `row_advancement_reason=blocked_force_switch` is about to fire in debug mode, the same record may also include `same_group_replan_probe`, a dry-run PAR feasibility check for the current participant set. This is diagnostic only and must not be interpreted as an env-side behavior change.
  - if the full same-group probe fails while some tuple members are already stationary at the row target, the same object may also include `moving_subset_replan_probe`, which reports whether the moving subset alone has a valid PAR tuple and what a recomposed synchronized tuple would look like with stationary participants held fixed.
  - if the env actually applies that bounded moving-subset recomposition at runtime, the same record also carries `moving_subset_runtime_result`, including the source tuple index, moving/stationary split, replan gate status, and a preview of the recomposed tuple rows
  - when `row_advancement_reason=final_row_release` is about to fire in debug mode, the same record may also include `final_row_release_retrigger_probe`, which snapshots and restores detector state and reports whether releasing the current tuple participants back to their saved long-range goals would yield `same_group_retrigger`, `different_group_retrigger`, `detected_but_empty`, or `no_retrigger`
  - if that full release already looks unsafe and some participants are already stationary on the final row, the same record may also include `final_row_partial_release_probe`, which asks the narrower hypothetical question “what if only the stationary participants were released back to RL while the moving participant(s) stayed in MAPF?” and reports the same status categories
  - if those release probes still say the final row is unsafe, the same record may also include `final_row_instability_probe`, which summarizes the mover’s target geometry, obstacle checks, target alignment, non-progress counters, and mover/stationary corridor-clearance metrics so callers can distinguish bad-target geometry from execution-level instability
  - for those same dangerous final-row cases, the same record may also include `final_row_execution_dynamics_probe`, which links the mover’s final-row target to the same-step MAPF execution trace and reports whether the failure looks like a raw policy action pointing the wrong way, an action that is too small relative to the desired velocity, or a later attenuation between applied command and actual motion
  - the same record may also include `final_row_diff_drive_feasibility_probe`, and the linked `mapf_execution_traces` may expose `*_diff_drive_projection` objects for raw/applied/desired actions. These projections answer a narrower integration question: even if a world-frame action looks goal-aligned, would `move_from_omni()` / `omni2diff()` on a `robot_mode: 'diff'` robot actually preserve linear progress, or would the action collapse into turn-in-place because the instantaneous heading error is too large?
  - the same record may additionally include `final_row_desired_velocity_probe` and `final_row_scaled_desired_direction_probe`, which ask two counterfactual controller questions under the exact same local RVO context: “would full desired velocity be safe?” and “would a desired-direction command at the current action speed be safe?”
  - a further debug-only config-gated runtime experiment may appear in traces as `final_row_direction_correction_*` fields inside `mapf_execution_traces`; this means the env temporarily rewrote a dangerous final-row mover's action to the same speed but desired direction. This experiment is currently disabled in the canonical debug config because the integrated robots still execute through differential-drive conversion (`move_from_omni()` / `omni2diff()`), so a world-frame desired-direction correction can still degenerate into turn-in-place behavior instead of real translational progress.
  - `collision_events`: one collision-context record per terminal collision, including the collision type plus env-side execution context (agent mode, solver type, participant set, tuple index, raw/modified action, speed-cap/yield flags, neighbor count used by RVO, `vo_flag`, and `min_exp_time`).
  - `stall_classification`: one episode-level classification derived from the above traces, used to distinguish tuple-group blocking from poor MAPF goal tracking and other measured non-progress modes.
- **Reset**: On env reset, call `DeadlockDetector.reset_episode()`, `StateManager.force_reset_all_agents_to_rl_rvo(num_agents)` (or reset_episode), and clear PARExecutor and coordinator state so no stale paths remain.

## Dependencies and assumptions

- **Semantics**: gym_env assumes detector is stateless per step given agent_states/neighbor_states and step_counter; PAR coordinator returns a single solution per prepare_par_execution; executor is stateful (path index, substep) until reset.
- **Config**: Deadlock config (trigger type, speeds, cooldown, PAR timeouts, grid resolution) is passed from env; when long-range is also enabled, coordinator reads gym_env.long_range_config for grid_resolution so PAR grid matches.
- **Idempotency**: prepare_par_execution is not idempotent (solver state); env calls it once per detected deadlock group per step. execute_par_step is called once per MAPF agent per step.

## Configuration and injection

- **Config**: Loaded from file in `enable_deadlock_resolution_mode(config_file)` or from defaults in _initialize_deadlock_modules. Keys match deadlock_resolution.contract.md.
- **Mock/test**: For tests without real PAR, one could inject a mock PARCoordinator that returns empty or fixed solutions; detector can be mocked to control trigger behavior.

## Error handling and fallback

- If prepare_par_execution returns unsuccessful or empty moves, env does not set PAR mode for participants (or sets mode but executor returns no action); agents may remain in RL_RVO or retry next step.
- If prepare_cbs_execution returns None (e.g. `cbs_mapf` not installed, grid build failure, or no solution), env does not set MAPF mode for that group; a one-line diagnostic is printed so the user can see that CBS failed. Resolving `cbs_mapf` import (e.g. `pip install cbs-mapf`) or grid/solver issues is required for agents to enter MAPF when using CBS.
- If prepare_rule_based_execution returns None (e.g. missing position/goal for a participant), env does not set MAPF mode for that group; agents remain in RL_RVO. Paths from rule_based are already in continuous coordinates; no grid-to-continuous conversion is needed.
- Exceptions in detector or coordinator are not always caught at env level; propagating them fails the step. Consider wrapping in try/except and falling back to pure RL for that step if needed.

## Conversion and validation

- agent_states/neighbor_states use env’s robot state format (position, velocity, goal as used by ir_gym). Detector expects position, velocity, goal; coordinator uses same for workspace and start/goal. No extra conversion except grid vs continuous in PAREnvironment (handled inside coordinator/executor).
