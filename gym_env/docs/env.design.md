# Environment Design (gym_env) — Internal

## Purpose

This document describes internal design choices and file layout for the gym_env module. It is for maintainers only; callers must rely on [env.contract.md](env.contract.md).

## Code organization

- **gym_env/envs/mrnav.py**: Thin Gym wrapper; delegates observation_space, action_space, step, reset, render to `ir_gym`. Forwards deadlock mode APIs to `ir_gym`.
- **gym_env/envs/ir_gym.py**: Main implementation: inherits `ir_sim.env.env_base`, composes RVO (`rvo_inter`), optional deadlock_resolution (DeadlockDetector, PARCoordinator, PARExecutor, StateManager, ModeController), optional LongRangeNavi (GlobalPathPlanner, WaypointManager). Handles step with/without deadlock, reset with grid/waypoint rebuild, occupancy grid building for long-range and PAR.
- **gym_env/envs/rvo_inter.py**: Wrapper around `reciprocal_vel_obs` for RVO reward and VO computation.
- **gym_env/envs/reciprocal_vel_obs.py**: RVO velocity obstacle logic.
- **gym_env/__init__.py**: Registers `mrnav-v1` with Gym.

## Key design choices

- **Single step path**: `mrnav.step(...)` is the canonical rollout entry point. When `enable_deadlock_resolution` is True, `step(...)` routes exactly once into `_step_with_deadlock_resolution`, which builds agent_states/neighbor_states, runs detector, may call PAR coordinator, finalizes the applied action list, computes RVO reward once, and then applies dynamics/observation/movement reward once. `step_ir(...)` remains only as a legacy alias and must delegate back to `step(...)` in deadlock mode. When deadlock is disabled, the wrapper uses the original non-deadlock `step_ir` path (RVO + obs/reward/done).
- **Waypoint and goal alignment**: For long-range, waypoint managers are updated at the start of the step (or in the deadlock path); `robot.goal` is set to the current waypoint so that observation and reward use the current subgoal. Done is set when the final waypoint is reached.
- **PAR and long-range interaction**: When PAR is triggered, participants get a temporary WaypointManager filled with PAR path waypoints; on PAR completion, the original long-range WaypointManager is restored so the agent resumes following global waypoints.
- **PAR force-switch guard**: gym_env now applies an env-side guard only for `mapf + par_manager` waypoint force-switches. Before force-advancing to the next PAR waypoint, the env samples the straight segment from the current position to the candidate next waypoint against the planner-aligned occupancy grid from `_build_occupancy_grid_for_long_range()`. If that segment crosses an occupied cell, the force-switch is blocked for that step so PAR execution does not shortcut through a known obstacle.
- **Tuple-group progression details**: When PAR exposes synchronized waypoint tuples, gym_env keeps a group-level tuple cursor in `_par_tuple_group`. The tuple-row `reach_threshold` is aligned upward to the injected PAR waypoint-manager tolerance so row completion is not stricter than the per-agent PAR managers. Non-final rows may also force-advance after a sustained blocked streak (`2 * FORCE_WAYPOINT_SWITCH_STEPS`) to prevent indefinite all-must-reach stalls on stale rows. The group also carries a narrower `final_row_release_steps` threshold (`FORCE_WAYPOINT_SWITCH_STEPS`) so that a true final row can release the whole tuple group back to RL without waiting for another row to exist.
- **Single active tuple-group policy**: gym_env treats `_par_tuple_group` as a single active synchronized PAR execution. While that tuple group is active, new PAR solver invocations from later deadlock detections are skipped instead of overwriting the active group. This prevents `mapf->mapf` reinjection churn from repeatedly resetting the tuple index back to zero.
- **Debug trace contract for waypoint progression**: When deadlock `DEBUG_MODE` is enabled, `_step_with_deadlock_resolution` emits one `waypoint_progression_traces` record per agent-step into the deadlock episode JSON. Each record captures manager type (`long_range_manager` vs `par_manager`), waypoint index/stay-step before and after `WaypointManager.update()`, thresholds, `advancement_reason` (`distance`, `force_switch`, `blocked_force_switch`, `stationary_hold`, `none`), whether `update_waypoint_history()` was called, optional blocked-force-switch metadata (reason, next goal, occupied cell), and any post-step MAPF exit reason such as `PAR tuple group completed` or `stay_fail(...)`.
- **Debug trace contract for deadlock checks during active tuples**: When a new deadlock trigger fires while `_par_tuple_group` is still active, the env records `solver_skipped_reason=active_par_tuple_group_in_progress` in `deadlock_check_traces`, along with the current active tuple participants and tuple index. This is the intended signal that the env preserved the existing synchronized PAR execution instead of resetting it.
- **Debug trace contract for tuple blockers**: `tuple_progression_traces` now include `dominant_blocking_participant_id` and `dominant_blocking_distance_to_target` in addition to the full per-participant target-distance list. This gives the env-level debugging view a single explicit “current lagging participant” field for late-row PAR tuple stalls.
- **Debug trace contract for same-group replan probes**: When a non-final row is about to advance via `blocked_force_switch` and deadlock `DEBUG_MODE` is enabled, the env records a debug-only `same_group_replan_probe` object inside that tuple trace. The probe summarizes whether a dry-run PAR solve on the current participant set yields the same participants back, whether a fresh tuple group is available, and which participants are valid or invalid without changing runtime behavior.
- **Debug trace contract for final-row release probes**: When a tuple row is about to release via `final_row_release` and deadlock `DEBUG_MODE` is enabled, the env records a debug-only `final_row_release_retrigger_probe` object inside that tuple trace. The probe snapshots and restores `DeadlockDetector` state, rewrites the would-be released participants to their saved long-range goals, and reports whether release would lead to `same_group_retrigger`, `different_group_retrigger`, `detected_but_empty`, or `no_retrigger` without changing runtime behavior.
- **Debug trace contract for final-row partial-release probes**: If the full final-row release probe already marks the release as unsafe, the env may also record a debug-only `final_row_partial_release_probe` object. This probe hypothetically releases only the stationary participants on the final row back to their saved long-range goals while keeping the moving participants on their current MAPF/final-row goal, then reports whether that narrower release would still yield `same_group_retrigger`, `different_group_retrigger`, `detected_but_empty`, or `no_retrigger`. This is diagnostic only and must not be treated as active runtime policy.
- **Debug trace contract for final-row instability probes**: For the same dangerous final-row cases, the env may also record a debug-only `final_row_instability_probe` object. This probe captures mover-to-target geometry, target-cell occupancy, straight-segment obstacle checks, current-goal vs row-target consistency, mover non-progress counters, and mover/stationary pair corridor-clearance metrics. Its purpose is to distinguish bad-target geometry from stationary-hold blocking versus execution-level convergence failure.
- **Debug trace contract for final-row execution dynamics probes**: For those same dangerous final-row cases, the env may additionally record a debug-only `final_row_execution_dynamics_probe` object. This probe joins the mover's final-row target with the same-step MAPF execution trace, exposing desired velocity, raw/applied/actual motion vectors, speed ratios, goal projections, speed-cap/yield flags, RVO neighbor counts, `vo_flag`, and lightweight diagnostic tags such as `raw_action_opposes_goal`, `applied_action_small_vs_desired`, or `actual_motion_small_vs_applied`. Its purpose is to separate policy-side action generation failure from env-side attenuation or local execution drift.
- **Debug trace contract for diff-drive feasibility probes**: For the same dangerous final-row cases, the env may also record a debug-only `final_row_diff_drive_feasibility_probe` object, and the per-step `mapf_execution_traces` may carry `raw_action_diff_drive_projection`, `applied_action_diff_drive_projection`, `desired_velocity_diff_drive_projection`, and `same_speed_desired_direction_diff_drive_projection`. These records project world-frame omni commands through the robot's differential-drive `omni2diff()` layer, exposing heading error, predicted `(v, w)`, linear-speed shrinkage, and whether the command would collapse into turn-in-place. Their purpose is to distinguish “world-frame direction is good” from “the command is not actually executable on the diff-drive robot in this step.”
- **Debug trace contract for final-row desired-direction probes**: For the same dangerous final-row cases, the env may also record two counterfactual debug-only probes: `final_row_desired_velocity_probe` tests whether a full-speed desired-velocity command would be locally safe under the current RVO context, while `final_row_scaled_desired_direction_probe` tests whether reusing the current action speed but rotating the command onto the desired-velocity direction would remain locally safe. Together they distinguish “desired direction is unsafe” from “full desired speed is too aggressive but direction-corrected motion at current speed is viable.”
- **Experimental final-row direction correction (currently disabled in canonical debug config)**: gym_env also contains a bounded runtime experiment behind `FINAL_ROW_DIRECTION_CORRECTION_ENABLED`. When enabled, it may replace a dangerous final-row mover's current MAPF action with a same-speed desired-direction action if that replacement is locally RVO-safe. Current debug evidence shows that this world-frame correction is not yet a valid fix path for `mode8_long_range.yaml`, because the robots are still `robot_mode: 'diff'` and `move_from_omni()` converts the corrected action through `omni2diff()`, which can collapse the correction into pure turning with zero linear motion when heading error is large. Keep this path disabled in the canonical debug config unless that diff-drive mismatch is being studied intentionally.
- **Moving-subset tuple replan candidate**: Before a non-final PAR row falls back to `blocked_force_switch`, gym_env may attempt a bounded PAR replan on only the still-moving subset when the row is late enough in the tuple sequence and that tuple lineage has not already consumed its single moving-subset replan budget. If this succeeds, stationary participants are held on their current tuple target while movers receive fresh PAR waypoints, the tuple trace records `row_advancement_reason=moving_subset_replan`, and the same record includes `moving_subset_runtime_result` describing the applied recomposition. This is a real env behavior change, not a debug-only probe.
- **Debug trace contract for collisions**: When deadlock `DEBUG_MODE` is enabled and `observation_reward()` detects a collision, gym_env emits a `collision_events` record that joins the collision type and RVO context (`vo_flag`, `min_exp_time`, neighbor count used by RVO) with the agent's control context for that step (`raw_action`, `modified_action`, speed-cap/yield flags, solver type, participant set, tuple index, current waypoint index, and current goal).
- **Planner-vs-simulator overlay contract**: For `robot_obstacle` collision events only, gym_env also builds a planner-aligned overlay payload from `_build_occupancy_grid_for_long_range()`, the colliding agent's best available path/waypoint list, and the simulator-reported obstacle geometry. The logger writes `collision_overlays/*.png` and `collision_overlays/*.json`, and appends a small `planner_simulator_collision_overlays` summary entry into the episode JSON. The overlay classifies the collision point as `planner_occupied_sim_collision`, `planner_free_sim_collision`, or `planner_out_of_bounds_sim_collision`.
- **Occupancy grid**: Built in `_build_occupancy_grid_for_long_range()` from world dimensions and obstacles (polygons, circles, lines); same grid resolution as long_range_config (and PAR when aligned). Used by GlobalPathPlanner and by PAREnvironment for PAR solver.

## Consistency with contract

- Observation/action spaces are defined in ir_gym and exposed unchanged by mrnav.
- Step return format (obs_list, reward_list, done_list, info_list) is consistent whether deadlock is on or off; info_list may carry waypoint_index and done flags for long-range.
- Reset clears all internal state (detector history, state manager, executor, waypoint managers) and rebuilds waypoints when long-range is enabled.

## Known limitations and TODOs

- Waypoint separation (min distance between agents’ waypoints) can be disabled in code; re-enabling may require tuning.
- PAR cropping (PAR_DISABLE_CROP) is on by default; sub-map cropping is off for debugging.
- Some debug prints remain in long-range and PAR paths; consider gating by a verbose flag.
